# How established job portals acquire jobs

Researched 2026-10-30 against first-party portal, ATS and standards documentation. This is a source review, not a measured inventory or implementation. No employer was contacted, partnership requested, job collected in bulk, account purchased or external record changed.

## Finding

The reviewed portals document several acquisition paths: recurring crawling of public sites, employer-supplied career-site URLs, ATS/feed integrations, and programmatic posting. There is strong evidence that this is an established problem with established solutions. There is no evidence here for the stronger assertion that most portals use one shared automatic employer-discovery technique, or that a complete public employer registry exists.

The practical model is a maintained source directory fed by several discovery channels. Discovery finds and verifies a source; a separate recurring collector maintains its jobs. This is an architectural inference from the documented workflows below, not disclosure of the portals' proprietary implementations.

The [Indeed Job Sync API](https://docs.indeed.com/job-sync-api) is an ATS-partner GraphQL integration for create/upsert/expire/status operations. Its presence should not be mistaken for an unauthenticated API to search Indeed's entire employer/job directory.

Google's [Indexing API quickstart](https://developers.google.com/search/apis/indexing-api/v3/quickstart) requires a service account and verified Search Console ownership. It is useful later for distributing our own eligible public job pages, not for discovering other employers' URLs through a global read endpoint. Google's [usage guide](https://developers.google.com/search/apis/indexing-api/v3/using-api) limits the API to eligible `JobPosting` and specified livestream pages and prohibits quota circumvention.

## ATS distribution is an acquisition channel, not merely a scraper alternative

GoHire's own [integration directory](https://help.gohire.io/en/articles/3385844-what-job-boards-does-gohire-integrate-with) lists many portal partners, including Indeed, LinkedIn, Google for Jobs, ZipRecruiter, Adzuna, Jooble, Jora and Talent.com. Workable's [Adzuna integration](https://partners.workable.com/adzuna) specifically describes posting directly from Workable. These first-party ATS documents demonstrate multi-portal distribution relationships. They do not establish that our new portal already qualifies for the same partnerships, or that a partnership exports all of an ATS's customers to us.

Adzuna's [Joblift acquisition announcement](https://www.adzuna.co.uk/blog/adzuna-acquires-joblift/) describes Joblift aggregating partner boards, employers and staffing firms. That supports heterogeneous source acquisition, but is a corporate account of another platform rather than a technical specification of Adzuna's crawler. The [Adzuna developer overview](https://developer.adzuna.com/overview) is a read API for its existing inventory, not a published automatic employer-discovery algorithm.

## Patterns we can adopt

These are proposed implementation choices derived from the evidence, not claims that all reviewed portals implement them identically.

1. **Create separate source intake channels.** Automated discovery, an operator-imported employer list, employer-submitted career URLs, partner feeds, and source links found in existing postings should all produce candidate sources in the same directory. Preserve which channel and URL supplied the evidence.
2. **Validate a source before publishing its jobs.** Establish the relationship between employer website and ATS board, record the source URL/platform and supported geography, inspect a sample, and compare observed jobs to an expected total when the source supplies one. LinkedIn's explicit company/source/expected-count onboarding fields are a useful model.
3. **Use a collection contract per source.** Record whether it supplies a complete snapshot, paginated complete listing, incremental events, or search-only partial results. Preserve pagination/progress and distinguish empty, failed and incomplete responses. Only complete successful snapshots can establish absence-based closures.
4. **Add cooperative intake as the catalogue grows.** Let verified employers submit or claim a career-source URL and supply an XML/JSON feed. A feed protocol and a source-directory interface can coexist with crawler discovery; neither requires building an employer ATS.
5. **Retain source evidence and canonical employer application links.** Separate source record IDs from canonical vacancy identity. Cross-posted jobs, agencies and multiple locations require reconciliation rather than counting every copy as additional supply.
6. **Measure freshness end to end.** Track employer posting time where present, first discovery, last successful observation, source collection completion and detected closure. Published partner feed schedules show why crawl cadence alone is an incomplete freshness claim.

## What the public evidence does not settle

- **Global seed discovery:** The reviewed portal docs mostly explain public-source crawling or onboarding already-known sources. They do not publish complete domain seeds, ranking formulas or a universal automatic employer directory.
- **Market coverage:** None of these methods establishes how much useful supply our users would receive in a particular country, profession or seniority. Broad catalogue goals need measured source/candidate coverage.
- **Our reuse rights:** Partner ingestion documentation describes sending data into those portals. It grants no general right to scrape those portals and republish their inventory. Source-specific access and reuse conditions remain separate from technical availability.
- **Robots and permission:** Jooble describes respecting robots exclusions and removal requests in its [employer explanation](https://jooblehelpcenter.freshdesk.com/en/support/solutions/articles/60000037148-how-did-my-vacancies-appear-on-jooble-). Our crawler should respect exclusions. [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html) says robots rules are not access authorization; a crawl-allowed URL is not itself a licence to redistribute its content.
- **Live performance:** No polling claim was independently benchmarked here. These are vendor-documented behaviors, not verified source uptime, parser quality, job availability or delivery guarantees.

## Conclusion for this project

The user's core hypothesis is supported: established portals already solve acquisition using multiple public-source and cooperative channels. Our missing capability is a sustained source-discovery and onboarding process connected to the existing collector. A practical next design should combine automated employer/career-site discovery with a persistent source directory, per-source validation and scheduled maintenance; add inbound employer/feed intake as a complementary channel. The exact automated bootstrap strategy needs its own evidence and small validation run rather than extrapolation from large portals' private infrastructure.
