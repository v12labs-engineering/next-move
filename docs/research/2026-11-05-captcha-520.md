# 2Captcha HTTP 520 investigation

The task requires a real Browserbase challenge to clear and the public demo server
to accept its response. A paid task ID, solver answer, response token alone, or
local test pass does not satisfy that requirement. No employer applications are
submitted or retried in this investigation.

## What the evidence establishes

The previous run recorded HTTP 520 from `api.2captcha.com/createTask`. Its log did
not retain a provider request ID or response classification, so the precise
upstream cause cannot be reconstructed. In this investigation, the same deployed
account returns HTTP 200/errorId 0 with a positive balance. A controlled upload of
the same challenge as PNG (320,835 bytes) and JPEG (48,647 bytes) returned HTTP 200
and accepted task IDs for both. Thus invalid credentials, exhausted balance, and a
consistently rejected PNG are not supported explanations. No new 520 has yet been
reproduced; that limits any claim about the historical provider failure.

[2Captcha documents](https://2captcha.com/api-docs/error-codes) non-200 responses
as technical/maintenance or malformed-request failures, separate from its JSON
API error codes. The existing bounded retries remain; logs now add a validated
Cloudflare request ID and JSON/HTML classification without keys, images, or raw
response bodies. An ambiguous lost create response is never automatically retried.

Live tests exposed independent application bugs after successful task creation:

- Generic rendered-grid screenshots miss the faster reCAPTCHA recognition path.
  Original sprite pixels and dynamic replacement tiles are now composed into a
  JPEG and sent with `imgType: recaptcha`, following the
  [provider's extraction example](https://2captcha.com/blog/recaptcha-recognition-using-grid-method).
  Unsupported/unreadable image layouts retain the generic screenshot path.
- Verify could be clicked before dynamic replacements loaded. The challenge then
  requested checking the new images, and a changed view caused immediate failure.
  Dynamic grids now wait for replacements and request another answer. They only
  Verify when the provider reports no remaining matching tiles. Changed pictures
  discard the previous answer and recapture within a shared bounded budget.
- Six seconds was insufficient for some live replacement images. Replacement
  loading gets up to 15 seconds within the unchanged two-minute solver deadline.
  All rounds and HTTP retries share a maximum of six task-creation attempts;
  repeated HTTP failures still stop after three attempts for that request.

The early test harness ran in Seoul with a Virginia browser, making guarded CDP
operations slow. The final private harness uses Virginia for both. Production
already chooses a nearby Browserbase region; its region policy is unchanged.

## Evidence and validation

Private raw diagnostics are in `.local-data/captcha-520/`; no credentials or
response token values are printed or copied into this report. Browserbase's own
solver is disabled for these tests, so an accepted result must come from our
2Captcha path. The temporary route is preview-only, authenticated to the owner,
restricted to fixed public demos, and time-limited.

Current local verification: 54 focused CAPTCHA/Telegram tests pass. The Chrome
pixel regression checks both 3x3 and 4x4 images, replacement-tile composition and
exclusion of selection outlines. Typecheck and targeted lint pass.

## Real accepted result

At 2026-11-05 02:35:09 UTC (08:05:09 IST), Browserbase session
`97362808-c78a-43aa-a727-52e8c7054441` cleared a real 4x4 reCAPTCHA v2 Enterprise
challenge using 2Captcha. The original-image payload was 35,766 bytes. Our solver
reported `cleared` after 15,573 ms. The complete public-demo test took 33,059 ms.
The browser had a response token, the challenge was absent, and clicking the
demo's Check button returned `Captcha is passed successfully!`, `success: true`
and `tokenProperties.valid: true`. Browserbase's own solver was disabled.

The demo also reported Enterprise risk score **0.1**. This is real token validity
and demo acceptance, not proof that an employer enforcing a higher risk threshold
will accept it. Dynamic 3x3 recovery and provider availability remain separate
reliability concerns; no guarantee of every CAPTCHA or employer acceptance is made.

Private evidence: `.local-data/captcha-520/success-enterprise.json`,
`success-enterprise.png`, and `live-settle.log`. The public screenshot contains
no key, candidate data, cookies, or response-token value.

## Remaining reliability limit

A second final-code test received a dynamic 3x3 challenge. It progressed through
six accepted solver tasks but exhausted the task cap with a visible challenge and
no token (session `25b35726-3e33-40c3-844a-fe87d2aea5ab`, 90,980 ms total).
Exploratory previews allowing ten tasks and one guarded widget refresh also failed
while waiting for replacements. Those experiments were not shipped; the workspace
and production retain the verified six-task implementation. The final experimental
session was `046e92b5-d248-4028-957a-61233db065db`, with replacement timeout and no
clearance. These are failures, not application receipts.

Telegram handoff for unsupported, stalled or exhausted challenges. No employer
applications were submitted or retried. Local changes remain uncommitted.

All nine temporary diagnostic previews were removed successfully. The production
