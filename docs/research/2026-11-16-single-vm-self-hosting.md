# Moving job-search off Vercel and Supabase Cloud

Reviewed November 16, 2026. This assessment uses the repository and its working tree, the installed dependency documentation, and provider documentation. Production settings, current traffic, storage usage, failure recovery, VM inventory, and application throughput were not measured.

## Decision

Run the application on one x86-64 Linux VM with Docker Compose. Keep Next.js, the AI SDK, and Workflow SDK. Replace Vercel's managed execution backend with Workflow's Postgres World, Vercel Cron with systemd timers, and Vercel AI Gateway with a compatible model endpoint. Run Supabase's open-source stack on the VM to preserve the existing Auth, PostgREST, Storage, and row-level security contracts.

This gets the app off both managed platforms. If the goal also includes removing Supabase software, treat that as a second migration. Stock Postgres can retain much of the schema and business SQL, but the app would need to replace authentication and cookie sessions, the Supabase data API, object storage, and the way authenticated identity reaches RLS policies. Existing user IDs, foreign keys, and service-only permissions need to retain their meaning in that migration. [Account migration](../../supabase/migrations/202610290001_public_accounts.sql) · [Session helper](../../lib/server/session.ts) · [Supabase license](https://github.com/supabase/supabase/blob/master/LICENSE)

## OVHcloud Gravelines reliability

VPS-2 in Gravelines is a reasonable month-to-month pilot if the application can tolerate a recovery window. The VPS hosts the web app, Postgres, Workflow, and scheduling in one failure domain. A machine failure therefore interrupts those components together. OVHcloud's status page publishes selected incidents and current component states. It provides insufficient evidence to calculate uptime for a specific VPS-2 or to promise a restore time.

**SLA and support.** OVHcloud India advertises 99.9% VPS availability, equivalent to about 43 minutes per 30-day month. The India VPS contract gives non-Starter tiers a 10% or 50% service credit for qualifying unavailability, subject to thresholds and exclusions. Its definition requires loss of access and inability to reboot for more than three consecutive minutes after an incident ticket is opened. The contract limits coverage to OVHcloud's VPS service. Standard support targets a first reply within eight business hours for critical incidents and lists a 24/7 incident chat. Recovery time depends on the failure. [VPS product](https://www.ovhcloud.com/en-in/vps/) · [India VPS contract, section 6](https://storage.gra.cloud.ovh.net/v1/AUTH_325716a587c64897acbef9a4a4726e38/contracts/e56b7c1-Conditions_Particulieres_VPS-IN-2.1.pdf#page=4) · [India support comparison](https://www.ovhcloud.com/en-in/support-levels/plans/)

**Public incident evidence.** The Gravelines VPS network and infrastructure components showed operational when checked on November 16, 2026. [OVHcloud VPS status](https://bare-metal-servers.status-ovhcloud.com/)

- On October 9 and 13, some Gravelines VPS were unreachable during incident windows of 13 and 9 minutes respectively. On October 24–25, a cooling issue made some Gravelines VPS unreachable. The published start and end times span 9 hours and 51 minutes, and OVHcloud reported that most services were back earlier. The affected hosts and individual downtime vary across these incidents. [October 9](https://bare-metal-servers.status-ovhcloud.com/incidents/h98w5krk8fs1) · [October 13](https://bare-metal-servers.status-ovhcloud.com/incidents/hxqybch5twd7) · [October 24–25](https://bare-metal-servers.status-ovhcloud.com/incidents/jqqkp50j9snr)
- On November 5, GRA6 backup and image operations were unstable for 3 hours and 9 minutes. The incident involved errors or delays creating, restoring, and managing VPS backups and images. [OVHcloud GRA6 incident](https://bare-metal-servers.status-ovhcloud.com/incidents/773pnt6fs1tm)
- On November 11, VPS management API operations experienced slow responses and intermittent errors over 2 hours and 9 minutes, including in Gravelines. [OVHcloud VPS API incident](https://bare-metal-servers.status-ovhcloud.com/incidents/nf7cgmq7tqqj)
- The 2021 fire destroyed Strasbourg SBG2 and affected nearby buildings on that campus. Strasbourg is a separate site from Gravelines. The incident shows the value of a recovery copy stored outside the hosting site. [French BEA-RI investigation](https://www.igedd.developpement-durable.gouv.fr/IMG/pdf/rapport_ovh_67_vdif_cle01cf13.pdf)

**Recovery.** VPS-2 in a full datacenter includes one daily system restore point retained for 24 hours. Attached disks are excluded. The paid option retains seven daily points, and the product page describes replication within the same datacenter. OVHcloud's KVM console and rescue mode help diagnose guest boot or networking issues. Keep an encrypted copy of the Supabase database, Workflow database, and Storage objects in a separate provider or location so the app can be rebuilt if the VPS or OVHcloud management service is unavailable. [VPS backup guide](https://docs.ovhcloud.com/en/guides/bare-metal-cloud/virtual-private-servers/using-automated-backups-on-a-vps) · [VPS product options](https://www.ovhcloud.com/en-in/vps/) · [Rescue mode](https://docs.ovhcloud.com/en/guides/bare-metal-cloud/virtual-private-servers/rescue)

During the pilot, probe the app and a DB-backed endpoint from outside OVHcloud, including from India if that is where users will connect. Watch application latency, DB latency, queue backlog, and restarts during scheduled VPS backup and catalog refresh. Restore to a clean host without calling OVHcloud's backup API, measure recovery time and data age, verify auth and object reads, and reconcile any uncertain application submissions before resuming automated sends. Where the pilot requires less than a day's potential data loss, set the independent backup cadence or use Postgres point-in-time recovery according to the required recovery point.

## Cutover and verification

The selected target is **OVHcloud VPS-2 in Gravelines, monthly with no commitment**. The last configurator quote was ₹953/month before tax. Run Next.js, self-hosted Supabase, Workflow Postgres World and the scheduler on this host. Keep remote browsers, model inference, and the SMTP relay external. Use a separate host only for the recovery drill. This is an execution plan. The machine, backup destination, and domain still need to be set up and the tests are pending. [VPS-2 configurator](https://www.ovhcloud.com/en-in/vps/configurator/?planCode=vps-2027-model2)

### 1. Identify the source and pin the release

- Match the currently promoted Job Search deployment to its Supabase project and record the release commit, app domains, Postgres major version and extensions, applied migrations, active browser provider, Webhook URIs, and enabled features. [The repo manifest](../../staging/project.json) is labeled staging even though it names the `job-search` Vercel project. Resolve the actual live pair before exporting user data. Keep the in-progress Boat changes outside the baseline unless the live release already contains them or they are deliberately included in a tested release.
- Inventory data by schema and bucket. Record counts for Auth users, profiles, resumes, application runs by status, receipts, catalog and matching rows, plus Storage object counts and bytes. Record pending workflows, DB leases, delayed retries, Telegram outbox work, and browser sessions where enabled. Collect counts and IDs in private evidence without logging candidate contents.
- Choose the owned public hostname and the Supabase HTTPS endpoint. If the live URL is only a Vercel-managed `vercel.app` alias, establish an owned hostname and use the old alias as a temporary redirect during the transition. Record the DNS records, callback allowlist and email templates, and the Telegram webhook destination. Lower a currently owned domain's DNS TTL ahead of the cutover. [Vercel deployment domains](https://vercel.com/docs/domains/working-with-domains/deploying-and-redirecting)

### 2. Build the VM release and deploy it privately

- Set up an x86-64 Linux VPS with Docker Compose and a TLS reverse proxy. Pin the app image, Supabase Compose revision, and database major version. Build the locked Node 24 app in CI using the intended `NEXT_PUBLIC_SUPABASE_URL` and public key for that environment. Keep runtime secrets outside the image. Persist DB and Storage volumes. Publish the reverse proxy only, restrict administrative access, and verify from another network that Postgres, Studio, and worker ports are private. [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting) · [Docker firewall behavior](https://docs.docker.com/engine/network/packet-filtering-firewalls/) · [Supabase Docker setup](https://supabase.com/docs/guides/self-hosting/docker)
- Add the compatible Postgres World package, a private database and role on the same Postgres instance, and Next.js startup instrumentation to start its worker. Bootstrap the Workflow database and use a session-capable connection. Keep `/.well-known/workflow/v1/flow` available to the internal worker and unreachable through the public proxy. Keep the inspection UI private. Use independent, conservative concurrency settings for Workflow and browser work. [Postgres World](https://workflow-sdk.dev/worlds/postgres) · [Next.js configuration](../../next.config.ts)
- Use new Supabase signing keys and API keys, SMTP, the existing browser provider, a direct HTTPS model endpoint, and isolated test credentials. Adapt the Vercel/Supabase Cloud-specific staging checks to validate the exact intended self-hosted origin and DB rather than bypassing those protections. Switch scheduled work to local systemd timers that authenticate with `CRON_SECRET`. Keep all timers disabled while preparing the target. ### 3. Test both kinds of restore

1. **Supabase Cloud import rehearsal.** Restore into a private Compose environment from the exact source schema and a permitted, protected export. Start with staging or scrubbed data. Exercise the final source export shape before accepting the cutover. Use Supabase's hosted-to-self-hosted roles, schema, and data procedure, preserving Auth UUIDs, grants, row-level security and migration state. Copy Storage content separately via the S3 protocol and reconcile bucket visibility, object counts and bytes, plus sampled object checksums and description reads. Confirm email OTP, token refresh, cross-account denials, service-only RPCs, resume and receipt reads. Existing sessions require reauthentication after the signing keys change. [Hosted project restore](https://supabase.com/docs/guides/self-hosting/restore-from-platform) · [Storage copy](https://supabase.com/docs/guides/self-hosting/copy-from-platform-s3)
2. **Self-hosted disaster recovery rehearsal.** From an exercised VM deployment, create an encrypted backup of the Supabase Postgres data and roles, Workflow Postgres state and queue, and Storage objects at a coordinated checkpoint. The simplest first backup procedure pauses writes and drains active workers during capture so both databases and Storage represent the same checkpoint. Include a manifest with the versions, release image digest, configuration references, backup timestamps and checksums. Store it outside OVHcloud. Keep decryption keys and system secrets separately recoverable. Restore onto a clean machine or isolated fresh host with empty volumes, using only that backup and the pinned release. Test independent of OVHcloud's snapshot and restore API.
3. **Prove recovery with side effects fenced.** Keep production Telegram, customer mail, real applicant credentials, and live employer sends blocked on the restored environment. Use an isolated test bot, test mailbox and the existing synthetic employer receiver with fictional applicant data. Start a synthetic Workflow run and capture a backup while it is durably waiting after a committed step. On the recovered host, resume the synthetic run, verify exactly one receiver submission and one persisted receipt, and prove that preexisting real application work cannot execute there. Restart the app during a separate synthetic run and verify recovery. [Synthetic application verifier](../../scripts/verify/verify-application-runner.mjs) · [Application receipt and retry rules](../application-pipeline.md)

Pass the restore gate only when the clean rebuild succeeds, source and restored data checks reconcile, and the isolated flow passes. ### 4. Freeze, transfer, and switch once

1. Freeze production deployments for the window. Disable Vercel Cron in project settings and prove the source stops scheduling new work. Establish a tested maintenance fence on all source entry points, including Vercel aliases, operator routes, application approvals, Telegram callbacks, and any direct data writers. Drain active source workflows and record what remains asleep, queued or uncertain. Cancel or fence future execution of those old runs and verify that no old worker can submit an application or reopen the database for writes after the final export. Resolve uncertain sends using the persisted intent, revision and employer receipt. [Vercel Cron controls](https://vercel.com/docs/project-configuration/project-settings#cron-jobs) · [Application recovery](../../lib/server/applications/auto-apply.ts)
2. With source writes paused, export the final database, sync Storage, and save an encrypted copy of this checkpoint off-host. Restore into the inactive OVHcloud target and repeat the reconciliation and private health checks. Start Postgres World with its own run state. Rebuild eligible work from the application's queues, leases, and revisions after reconciliation. Previous Vercel World run IDs belong to the old backend. Leave held and ambiguous sends pending review and let any old Boat sessions finish or be accounted for before dispatching replacement work. [Vercel World](https://workflow-sdk.dev/worlds/vercel) · [Catalog dispatch and lease](../../lib/server/catalog/dispatch.ts)
3. Verify HTTPS and auth redirects on the final hostnames from a private test client using a local DNS override and valid TLS. Switch the owned DNS and move the production Telegram webhook once if enabled. Preserve pending updates where supported and verify the destination and delivery with `getWebhookInfo`. Keep the old stack behind the maintenance fence while DNS caches expire. Smoke-test the new URL, authentication, data reads, safe writes and one durable workflow, then enable the new schedules in stages. Turn on application recovery and automatic sends last, after reconciling intents and confirming that only the VM can dispatch. [Telegram webhook API](https://core.telegram.org/bots/api#setwebhook)

### 5. Roll back or retire the old stack

- **Before the OVHcloud app accepts writes or sends.** Keep the VM worker dispatch and timers paused, restore the original DNS and webhook, then reopen the original app and scheduler after verifying that the VM is fenced.
- **After the first OVHcloud write or external send.** Pause admissions and dispatch on both sides and preserve a fresh destination export. Prefer fixing the issue on the VM. Returning to the old stack requires reconciling new database writes, object changes, and employer submission evidence with the old source first. A DNS-only reversal would expose stale state and could repeat a submission.
- Keep the original platforms available for an agreed observation window with background automation fenced. Confirm external uptime monitoring, backup uploads, the scheduled jobs, and live workflow completions. Retire the managed projects, old keys, Gateway/OIDC usage, and temporary redirect after the rollback window and once the recovery evidence is recorded.
